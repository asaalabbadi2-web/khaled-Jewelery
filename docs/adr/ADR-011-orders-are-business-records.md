# ADR-011: Orders Are Business Records, Not Invoices

**Status**: Accepted  
**Date**: 2026-07-13

## Rule

The `Order` aggregate is the canonical business record for a completed sale.
All downstream capabilities (Shipping, Notifications, ERP Sync, Analytics, CRM)
derive their data from `OrderCreated`. Nothing reads from `reservations` after
an order exists.

## Context

Without this rule, the system has no single record of "a sale happened":

- Reservations represent intent — the item is held but not sold.
- PaymentIntents represent authorization — money is collected but delivery is not committed.
- Neither alone answers "What did this customer buy? When? At what price?"

As capabilities multiply (Shipping, Returns, Analytics), each one would query
`reservations` and `payment_intents` separately, reconstructing the sale fact
from two tables. This violates Single Source of Truth (Architectural Principles).

## Decision

An `Order` is created atomically when payment is confirmed:

```
PaymentService.confirm()          → PaymentIntent(PAID)
    ↓
CheckoutService.confirm()
    ├─ OrderService.create_from_reservation()  → Order(CONFIRMED)
    ├─ reservation_repository.update_status()  → Reservation(COMPLETED)
    └─ outbox.enqueue(OrderCreated + ReservationConfirmed)
    ↓  [single commit via CheckoutUnitOfWork]
```

The `CheckoutUnitOfWork` wraps both `reservation_repository` and
`order_repository` in the same SQLAlchemy `Session` so the two writes
are atomic. A crash between them is impossible.

## Order vs. Invoice distinction

| Concept | Order | Invoice |
|---------|-------|---------|
| Domain | Commerce | Accounting |
| Created when | Payment confirmed | Order delivered / shipped |
| Contains | Item, amount, status | Tax breakdown, billing address, legal entity |
| Mutable | Yes (status transitions) | No (accounting record, immutable) |
| Owns | Shipping lifecycle | Revenue recognition |

Invoices are generated by the ERP (Flask) after delivery. They are NOT
created here.

## Order Lifecycle

```
PENDING          (reserved for future: COD, BNPL)
    ↓
CONFIRMED        ← created here, from confirmed payment
    ↓
READY_FOR_SHIPMENT
    ↓
SHIPPED
    ↓
DELIVERED
         ↘
       CANCELLED  (from any non-terminal state)
```

In the current flow, orders always start as `CONFIRMED` (payment already
received). `PENDING` is reserved for future payment methods where order
creation precedes payment confirmation.

## Inventory: AVAILABLE → RESERVED → SOLD

| Transition | Trigger | Where |
|------------|---------|-------|
| AVAILABLE → RESERVED | Reservation created | ReservationService |
| RESERVED → SOLD | Order created | ERP consumer of OrderCreated event |

The Commerce API does not write item status directly. The `OrderCreated` event
carries `item_id` so the ERP consumer can mark the item as SOLD without a
re-query. This upholds Single Writer for ERP-owned data.

## Downstream contract

Every capability that needs sale data must:
1. Listen to `OrderCreated` (for real-time processing), OR
2. Call `GET /api/v1/orders/{order_id}` (for on-demand lookup)

Never query `reservations` or `payment_intents` for business decisions.

| Future capability | What it reads |
|-------------------|---------------|
| Shipping (Sprint 7) | `OrderCreated.item_id`, `OrderCreated.order_id` |
| Notifications (Sprint 6) | `OrderCreated.reservation_id` → customer lookup |
| ERP Sync | `OrderCreated.item_id` → mark item SOLD |
| Analytics | `OrderCreated.amount`, `OrderCreated.currency` |
| Returns (Sprint 9) | `GET /orders/{id}` → current status |
| Customer Portal | `GET /reservations/{id}/order` |

## Enforcement

- A PR that reads `reservations.status` for post-payment decisions must be
  redirected to `orders.status`.
- A PR that writes to `payment_intents` from a Shipping or Notification
  handler violates Single Writer — reject citing this ADR.
- Adding a new downstream capability: always start with `OrderCreated` consumer,
  not a new column on `reservations`.
